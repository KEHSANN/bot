# Audit guarantees and boundaries

Implemented `audit_logs` records actor UUID (null for unknown login/system/operator), action, target type/id, PostgreSQL timestamp, outcome, reason code, request UUID, hashed peer and user-agent fingerprints, and allowlisted details. Login targets are admin UUIDs when known or username fingerprints when unknown. Role/permission changes record old/new IDs or known permission codes; status/settings capture constrained states/booleans. Passwords, tokens/digests, raw headers, arbitrary reasons, request bodies, usernames, descriptions and secret-bearing configuration are never copied into audit details. Fingerprints are pseudonymous, not anonymous.

Success audit and state-changing operations commit together. Audit insertion failure rolls back positive mutations and session/token issuance and returns 503. Authentication/authorization failures are logged after rolling back the failed operation. Refresh replay revocation normally commits with its denial event; if audit insertion alone fails, a separate restrictive revocation is attempted and the API still returns 503. The session can therefore be revoked without an audit row in this exceptional case. If PostgreSQL is unavailable neither audit nor revocation can be persisted; operations fail closed. This limitation is explicit, not a claim of lossless auditing during storage outages.

PostgreSQL statement triggers reject UPDATE, DELETE and TRUNCATE of audit_logs, including ORM updates and table-owner DML. There is no application update/delete audit endpoint. The non-owner runtime group in `deploy/runtime-role.sql` grants SELECT/INSERT only on audit_logs and no DDL/ownership; tests verify a non-owner cannot modify/delete/truncate records or disable their trigger. Migrations must use a separate privileged owner account.

**Not absolute immutability:** a database superuser/table owner can disable/drop triggers, alter/drop the table, modify backups or storage, or fabricate INSERT records. A compromised application database credential can fabricate inserts and change other business tables outside service auditing. No cryptographic chain, external WORM store or independent timestamp authority exists. Direct privileged SQL changes are not automatically actor-attributed by the service. Production requires restricted owner credentials, external database/host auditing, backups and monitoring.

Migration downgrade deliberately drops the audit table/trigger and loses that history. Downgrade/base lifecycle tests run only on disposable *_test databases. Do not use destructive downgrades in production as an audit-retention or rollback procedure.
